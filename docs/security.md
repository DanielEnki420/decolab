# Security model

What Decolab protects, against whom, and what it leaves to you. Read the
last section ("What Decolab does not protect against") before you put
anything on the Pi that you cannot afford to lose or to have read.

## What is worth protecting

| Asset | Where |
|---|---|
| Your passwords (Vaultwarden) | `DATA_DIR/vaultwarden`, encrypted by the clients |
| Your photos (Immich) | `DATA_DIR/immich` |
| Files on the share (Samba) | `DATA_DIR/nas` |
| What the household looks up (DNS) | Pi-hole; the query history is not backed up |
| Every generated secret | `SECRETS_DIR` (mode 700), and `config.tar.gz` in every backup |
| The backups themselves | `BACKUP_DIR`, the USB disk, the restic repository |

## Who it is built against

**Nobody from the internet.** Decolab opens no port to the internet and
expects no port forwarding on your router. Remote access is through
Tailscale only.

**A device in your LAN that turned bad**, for example a cheap smart plug, a
TV, or a guest's laptop:

- With `WEB_UI_ADDRESS=127.0.0.1` (the default) no web interface listens on
  the LAN. The LAN sees only DNS (53), Samba (139/445) and SSH.
- With `HARDENING=yes` and the firewall confirmed, only those ports are open,
  and only from `LAN_SUBNET`. The rule set is an allow list, for IPv4 and
  IPv6 alike.
- Samba asks for a password. It is generated by install.sh.
- SSH: no root login. With `SSH_PASSWORDS=no` keys only, switched on by the
  firewall's trial, so a missing key cannot lock you out.

**A device in your tailnet:** the firewall lets all of `tailscale0` in, so
it reaches every port of the host (SSH, DNS, Samba) and what you published
with `tailscale serve`; Perses and Pi-hole's dashboard have no login of their
own. Tailscale's access rules are the control here: restrict them, and check
what the Pi really applies with `bin/decolab-tailnet-ports TAILNET-IP`.

**A web page in your own browser**, while you are logged in to the panel:

- The panel accepts only this host's names in the `Host` header (against DNS
  rebinding).
- It checks `Origin` on login, and its cookie is `SameSite=Strict` and
  `HttpOnly`.
- It sends a strict Content-Security-Policy, and it has no route that
  changes anything.
- Its cookie holds the panel token itself. Cookies belong to a host, not a
  port: the browser also sends it to the other web interfaces on the same
  host. Who controls one of them can read the panel (read-only). Rotate the
  token by deleting `SECRETS_DIR/panel-token`, running install.sh and then
  `sudo systemctl restart decolab-panel` (it reads the token at start).
- About 64 slow connections can block the panel for a while. It is a
  dashboard; nothing depends on it.

**A service that is broken into** (a bug in one of the images):

- Every container drops all Linux capabilities and adds back only the
  measured ones. It runs with `no-new-privileges` and a memory limit, and
  where possible as a non-root user with a read-only root file system.
- Only the socket proxies talk to the Docker socket. Portainer, Watchtower
  and cAdvisor get the API calls they need, nothing more. The panel has no
  Docker access at all (its unit cannot open a Unix socket).
- Perses sits in a network with Prometheus only, and is read-only.
- The firewall lets containers reach the host for DNS only, not SSH, Samba
  or the panel. cAdvisor sees Docker's image layers, not the host's files or
  the containers' settings; Unbound cannot change its config.
- Not closed: a container may reach the LAN, the internet and the tailnet
  (forward chain), as any device in the LAN can.
- Two containers hold the keys to the host: the socket proxy behind
  Portainer and Watchtower may create containers, so a Portainer admin, or a
  poisoned Watchtower image, is root on the host. Both sit alone with it in
  an internal network.

**An image update that went wrong, or was poisoned:** every image is pinned
by digest. Nothing updates at a random time; an update is a Decolab release
you choose to install. Watchtower updates none of Decolab's containers.

**Your own mistakes:**

- install.sh checks everything before it changes anything, and never
  overwrites a file you changed.
- The firewall is applied on trial and switches itself off again unless you
  confirm it from a new login.
- Backups are rotated by count, not by age, so failing backups delete
  nothing.
- A USB mirror is never written from an empty source.

**Losing data:** three copies (local, USB, off-site with restic), and every
night a restore probe proves that the newest backup becomes a working service
again. What each probe proves, and what it does not, is written at the top of
each `scripts/restore-probe-*.sh`.

## Secrets

- Generated by install.sh, never by you, never in the repository, never in a
  command line: tokens go to curl on stdin, so `ps` does not show them.
- `decolab.conf` holds no secret, and it is read as data, never executed.
- The restic password is the only secret you must keep outside the Pi as
  well (INSTALL.md, step 6). Without it the off-site copy is lost.
- Every commit to this repository passes `tools/guard.sh` and gitleaks, and
  every push the whole history again (authors and tags included). CI checks
  it once more.

## What Decolab does not protect against

These are decisions, not oversights. Weigh them for your own setup.

- **Someone with the Pi in their hands.** The disks are not encrypted. Who
  takes the Pi or the USB disk can read the secrets, the photos and the
  share. Vaultwarden's entries stay encrypted with your master password.
  Keep the USB disk somewhere safe.
- **Someone with your user's login.** `DECOLAB_USER` is in the `docker`
  group, which is as good as root. Protect that login: SSH keys, and
  `HARDENING=yes`.
- **The publishers of the images.** Pinning by digest stops surprise
  updates. It cannot tell you whether the release you choose is trustworthy.
- **Whoever holds the release key.** Release tags are signed, and
  `bin/decolab-checkout` and `update.sh` refuse any other: a stolen GitHub
  account alone cannot ship code that root runs. The keys are the ones your
  first install placed in `/etc/decolab/release-signers`; that first
  checkout you trust on sight, as with any download. Read the changes of a
  release before you check it out.
- **The off-site server.** It sees only encrypted data. Who controls it can
  delete it, so the USB copy matters.
- **Telegram or ntfy.** Notifications pass through their servers. They
  contain host names and service states, no secrets. On the public ntfy.sh
  the topic name is the only lock: anyone who knows it can read along, so
  install.sh suggests a random one. Your own ntfy server with an access
  token avoids that.
- **A household device that uses DNS over HTTPS** bypasses Pi-hole. That is
  a matter of blocking, not of security.
- **Availability.** One Pi is one Pi. Decolab tells you quickly when
  something is down; it does not keep it up.
